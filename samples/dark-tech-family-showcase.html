Prompt Engineering

// 2022.11 — 2023

把想要的输出，写进一段自然语言指令。

  • Few-shot / CoT / ReAct / ToT
  • 单次调用，无状态、无工具、无记忆
  • 上限被模型能力锁死
02

Context Engineering

// 2024 — 2025

把模型每次推理能用上的信息，组装好再喂进去。

// 2024.Q4 — 2026+

把模型包进一套能自主循环的工程骨架里。

// INSIGHT
每一次主角升级，前一阶段都没死。它只是从「明星技巧」降级成「基础组件」——Prompt 仍然是 Context 的输入，Context 仍然是 Harness 的燃料。
PHASE_01 Prompt Engineering · 起源

把「想要的输出」写进一段话

2022.11 ChatGPT 起飞，所有人突然发现：会写 prompt 的人，效率碾压不会写的人。
// 一句话定义
Prompt Engineering 是把任务目标、约束条件、输出格式，全部编码进一段自然语言指令的工程实践。它的对手不是模型，是 prompt 写得不够清楚的自己。
// 三个里程碑
2022.03 InstructGPT · RLHF 把模型从补全器驯化成指令跟随者
2022.11 ChatGPT · 5 天 100 万用户，prompt 进入大众词汇
2023.03 GPT-4 · 长指令、复杂推理、code interpreter 全部起飞
// 一个最小可用的 prompt = 角色 + 任务 + 约束 + 格式 你是一位资深数据分析师。 任务：从下面的销售记录中找出环比下降超过 20%的产品。 # 输入 2025-06,iPhone 15,1200 2025-07,iPhone 15,890 ... # 输出格式（严格遵守） 产品名 | 下降幅度 | 建议动作 # 约束 - 只输出表格，不要解释 - 数字保留 1 位小数
PHASE_01 Prompt Engineering · 核心技巧

五把扳手，把模型拧到该有的位置

这些技巧在 2023 年集中爆发，今天仍然是写好 prompt 的肌肉记忆。
01

Few-shot

给 2-3 个例子，模型照葫芦画瓢。零样本跑偏时最便宜的兜底。

输入: 开心 → 输出: 😊 输入: 难过 → 输出: 😢 输入: 兴奋 →
02

CoT

Chain-of-Thought。让模型先写步骤再给答案，推理题立竿见影。

让我们一步步思考： 1. 列出已知条件 2. 列出未知量 3. 推导关系 4. 计算答案
03

ReAct

Reason + Act。模型边推理边调用工具，把思考和动作交织成轨迹。

Thought: 需要查汇率 Action: search("USD to CNY") Observation: 1 USD = 7.18 CNY Thought: 现在可以算了
04

ToT

Tree-of-Thought。多路推理 + 投票，适合需要探索解空间的任务。

候选解 A: ... 候选解 B: ... 候选解 C: ... 投票: B > A > C
05

Self-Consistency

采样多条 CoT 路径，少数服从多数。准确率换算力的典型打法。

for i in 1..N: chain = model.sample(prompt) answers.append(chain.final) return majority(answers)
// 这些技巧的本质
都是把「我想要 X」翻译成「模型能稳定输出 X」的协议。它们改善的是同一句话的命中率，不改变模型本身。
PHASE_01 Prompt Engineering · 局限性

写到天花板，问题就不在 prompt 里了

AutoGPT 2023.04 上线那天起，「自动循环 + 调工具 + 跨会话」的需求就把 prompt 撑破了。
×

单次调用

一次输入一次输出。没有循环，没有「试试不行再换」的余地。

input → model → output ↓ 结束
×

无状态

模型不记得上一轮说过什么。多轮对话靠历史塞进 context，不是真正记忆。

session_2.start() context: [] memory: ∅
×

无工具

模型只能吐文字。查不到实时数据、动不了文件、调不了 API。

capability: [text_in, text_out] no: [search, code, db, file]
×

无记忆

跨会话、跨用户、跨天，模型对你是陌生人。个性化无从谈起。

user_α == user_β today == tomorrow 没有任何长期状态
// 转场信号
当 prompt 写到第 17 版还是同一个地方出错，问题就不在 prompt 里。prompt 不是工程，是 prompt 之外的事太少了。开始往 context 里塞东西吧。
PHASE_02 Context Engineering · 为什么

窗口越大，塞得多 ≠ 答得好

2025.07 Anthropic 发表《Effective context engineering for AI agents》，把「喂什么进去」从技巧升级成学科。
// 核心命题
Context Engineering 是为模型每次推理精心挑选和组装信息的工程实践。 Prompt 写的是「怎么问」，context engineering 写的是「喂什么」。前者优化一行，后者优化一整套输入构造流水线。
// Context Rot
模型在长上下文中的检索精度不是线性下降，而是会随着上下文增长出现 非线性退化。堆东西 ≠ 喂好东西。
// 三条经验数据
▸ 多 needle-in-haystack 测试中，超过 60% 填充率后命中率陡降
▸ 中段信息比首尾更容易被忽略（lost-in-the-middle）
▸ 噪声指令会被模型当成真实指令执行
// 一个 200K 上下文的典型失败 [ system_prompt ] // 2K [ 10 个 tool definitions ] // 8K [ 5 篇 RAG 召回 ] // 12K [ 历史对话 50 轮 ] // 18K [ 当前用户问题 ] // 0.5K [ 一些「以防万一」的兜底 ] // 160K 噪声 // → 模型在 system 指令和「兜底」之间困惑 // → tool 定义被压在中间，命中率下降 // → 真正该被用的 RAG 片段被淹没 解法 = 选 + 压 + 排
PHASE_02 Context Engineering · 关键技术

五大模块，给模型准备一顿好饭

Context Engineering 不是单点技术，是一组协同的工程模块。每一块都在回答「这条信息该不该出现在这次推理里」。
01

RAG

检索增强生成。把私有知识从向量库召回到 context。

query → embed → vector_search(top_k) → rerank → 注入
02

Memory

把跨会话的事实、偏好、反馈存进可检索层。

short: 当前任务状态 long: 用户偏好 episodic: 关键事件
03

Tool Use

让模型在推理中调用外部能力。Function calling 是入口。

{ name, desc, schema } → model 返回 tool_call → 执行 → observation
04

MCP

Model Context Protocol。工具和数据源的标准化接口协议。

host ⇄ MCP client ⇄ server (tool/data) ⇄ resources / prompts
05

长上下文

1M token 窗口只是物理条件，关键是 placement 与压缩。

前后: 重要信息 中段: 避免关键 格式: XML/JSON > Markdown
// 协同规则
RAG 解决「事实」，Memory 解决「状态」，Tool 解决「行动」，MCP 解决「对接」，长上下文解决「密度」。五个一起用，单点优化收益被锁死。
PHASE_03 Harness Engineering · 是什么

模型是引擎，harness 是变速箱

2025 Anthropic 提出 Harness Engineering：把模型包进一套能自主循环、可验证、可治理的工程骨架。
// 一句话定义
Harness 是包在模型外层的工程骨架。它决定模型什么时候被调用、用什么工具、看到什么 context、产出怎么验证、错了怎么办、谁能拦下来。同样的模型，不同 harness，能力天差地别。
// 起源
2023.04 AutoGPT · 第一次让 LLM 自主循环
2024.10 Claude Computer Use · 模型直接操作系统
2025.02 MCP 协议 · harness 的标准化接口层
2025.08 Claude Agent SDK + Harness Engineering · 框架术语正式成型
// 一个最小 harness 的骨架 while not task_done: # 1. 组装 context context = build_context( system, memory, rag, tool_schemas, history ) # 2. 调模型 response = model(context) # 3. 执行动作 if response.tool_call: result = run_tool(...) verify(result) # 4. 写回状态 memory.update(...) # 5. 守门 permission.check(action) budget.consume(tokens) // 模型只负责第 2 步 // 其它四步都是 harness 的事

PHASE_03 Harness Engineering · 代表产品

同一时代，五个方向，各走各路

同一个 Claude 模型，套上不同 harness，呈现完全不同的能力边界。

// 关键观察
没有「最强 harness」，只有「最匹配场景的 harness」。挑 harness 的本质是挑 信任边界：哪些动作自动执行、哪些必须人审、哪些需要 rollback。
PHASE_03 Harness Engineering · 六件套

拆开任何 production harness，都是这六块

不管叫 Claude Agent SDK 还是 OpenAI Agents SDK 还是自研框架，六件套是骨架。
01 · LOOP

主循环

while not done: 组装 context → 调模型 → 执行 → 验证 → 写回状态。loop 的稳定性和退出条件决定 harness 死活。

02 · TOOLS

工具集

读、写、搜、跑命令、调 API。工具的设计比工具的数量重要十倍。每个 tool 必须有 schema、错误处理、超时。

03 · CONTEXT

上下文装配

把 system、memory、rag、tool defs、history 拼成最优输入。这是 phase_02 的全部积累。

04 · VERIFICATION

验证层

模型说什么都先验证。单元测试、类型检查、syntax lint、输出 schema 校验。harness 不验证 = 模型幻觉狂奔。

05 · SUBAGENT

子 agent

把任务拆给有独立 context、独立工具集的子 agent。是复杂任务的唯一解，也是 context rot 的主要解药。

06 · PERMISSION

权限闸

谁能跑、谁能删、谁能外发。production harness 的第一性问题是「这一刀切下去能不能撤回」。

// 经验
缺 loop 死循环，缺 tool 等于聊天，缺 context 模型瞎说，缺 verification 幻觉失控，缺 subagent 任务撑不开，缺 permission 老板不让上线。六件缺一不可。
// FUTURE 下一站 · Spec / Mission / Outcome Engineering

下一步：把「过程」也工程化掉

从 prompt → context → harness，下一个被工程化的对象，是任务的定义本身。
FROM → TO

Spec Engineering

2026 雏形

不写 prompt，写规格说明书。模型自己拆解、自己验收。人的工作从「写怎么做」变成「写要什么」。

FROM → TO

Mission Engineering

2026+ 探索

把目标当 first-class object 传给模型。harness 不再被指定流程，而是被指定「结果」。

FROM → TO

Outcome Engineering

2027+ 雏形

模型直接对接业务 KPI，对效果负责。不再交付「做完了」，而是交付「指标涨了 X%」。

// 关键判断
真正的范式转移不在新模型，而在「人给机器的输入」这一端的形态升级。今天我们写 prompt，明天我们写 spec，后天我们写 outcome。每升一层，人类的注意力就从过程里抽身。
